# Number

+ `Min Normal` is the smallest positive **normal** value, `Min Subnormal` the smallest positive **subnormal** one (`=` when the format has no subnormals).
+ `0x00` / `0x80` are the values of those two byte patterns, given only for the 8-bit and narrower formats where a byte is the whole story.
+ For the block-scaled formats (MX*, NVFP4) `Max` / `Min` describe the **element** format; the block scale multiplies the whole range by up to $2^{\pm127}$.
+ Verified against `torch` 2.13 and `ml_dtypes` 0.5.4 (`finfo`, plus bit patterns read back through `view()`).

+ PyTorch column: ✓ = a real `torch.<name>` dtype, ⚠️ = representable but only through a wrapper / limited op support, ❌ = no dtype of that name.
+ PyTorch has no `float8_e4m3` (bare), no `float6_*` and no separate `float4_e2m1fn`: the FP4 dtype is `torch.float4_e2m1fn_x2`, i.e. **two elements packed in one byte** — the packing is part of the type. `ml_dtypes` has the unpacked and 6-bit ones.
+ `torch.int1` … `torch.int7` and `torch.uint1` … `torch.uint7` exist in recent builds as *shell dtypes*: they carry the right element size but almost no kernel supports them.

## Formats that are strategies, not types

| Concept     | Nature                           | Technical Details                                                                                       | Use Cases                       |
| ----------- | -------------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------- |
| **TF32**    | **compute precision format**     | 19-bit (1-8-10), used internally by Ampere+ Tensor Cores, still stored and addressed as FP32            | NVIDIA GPU matrix acceleration  |
| **FP8**     | **per-tensor scaled FP8**        | `float8_e4m3fn` (forward) + `float8_e5m2` (backward) with an FP32 scale per tensor; **no block scale**, and there is no NVIDIA format called "NVFP8" | Hopper / Blackwell training and inference |
| **MXFP8**   | **OCP MX specification**         | elements `float8_e4m3fn` **or** `float8_e5m2`, block size 32, scale `E8M0`                              | general AI training/inference   |
| **MXFP6**   | **OCP MX specification**         | elements `FP6 E3M2` or `E2M3`, block size 32, scale `E8M0`                                              | rarely implemented in hardware  |
| **MXFP4**   | **OCP MX specification**         | elements `FP4 E2M1`, block size 32, scale `E8M0`                                                        | extreme compression scenarios   |
| **NVFP4**   | **NVIDIA variant specification** | elements `FP4 E2M1`, block size 16, scale `E4M3` + `FP32` tensor scale                                  | Blackwell GPU inference         |
| **FP4e0m3** | **theoretical format**           | 1-0-3, a sign-magnitude fixed point identical to INT4 divided by 8, no hardware uses it                 | ❎ no practical application      |

## The one that keeps biting: E4M3 comes in three flavours

Same layout `1-4-3`, three different value sets, and the name alone does not tell you which one:

| | Inf | Max | NaN encoding | where |
| - | --- | --- | ------------ | ----- |
| `float8_e4m3`     | ✓ | 240 | `S.1111.xxx`, x≠0 | `ml_dtypes`, IEEE-style |
| `float8_e4m3fn`   | ❌ | **448** | `S.1111.111` only | **OCP OFP8**, `torch`, NVIDIA hardware |
| `float8_e4m3fnuz` | ❌ | 240 | `1.0000.000` only | AMD, bias 8, no -0 |

`fn` = **f**inite (no Inf), `uz` = **u**nsigned **z**ero (0x80 becomes NaN instead of -0). `float8_e8m0fnu`
is `fn` + `u` with a single NaN at `0xFF` and no zero at all.
