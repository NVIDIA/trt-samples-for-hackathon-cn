# baselines/ —— 已验证的参考运行

这里存放**在已知机器上实跑并核对过的完整输出**，用于：

1. 换到新环境时，有一份「同一套脚本在正常机器上长什么样」的对照
2. 验证套件本身没被改坏（任何修改后重跑一遍，应能复现）

## nvref-pro5000-615.44-xeon-w5-3425_20261030

**2026-10-30 的套件可用性验证运行。退出码 0，耗时 5 分 32 秒。**

### 机器

| 项 | 值 |

### 复现结果

| 测试台 | 结论 |
| --- | --- |
| **T1** 完整发射基准（41 项） | **全部在 ±4.1% 以内**，`9c(n=8)` = 512 ns 逐位相同 |
| **T2** 往返拆分 | `host` 4285（参考 ~4282）、`event` 2432（~2432）、`issue@1024` 1388（~1388） |
| **T6** 逐核扫描 | 除 0 号核外极差 **4.4%**，优于 8.9% 的噪声基线 |
| **T6** 槽位扫描 | 三配置极差 **1.4%**，两张卡等价（均在 node0） |
| **T8** QPS | 当时因无模型数据而自动跳过，写了 `08_qps_status.txt` 说明原因（该测项的压测器此后已移除，见 `诊断手册.md` 第十一节） |

**时隔 5 周、换了驱动小版本、在 powersave 且无 root 的容器里重跑，
41 个测项无一超过 ±4.1%** —— 套件的可复现性与预热兜底都经受住了检验。

### 本次运行暴露的两件事

**① 0 号核确实该避开（实证）**

| 核 | min (ns) |
| --- | --- |
| **0** | **1840.1** |
| 1 ~ 16（其余 9 个采样核） | 1330.8 ~ 1389.2 |

0 号核比其余核慢 **+38%**。含 0 号核时极差 38.3%，剔除后仅 4.4%。
`pick_core.sh` 的「避开 0 号核」规则**不是经验之谈，是本机就能看到的事实**。

> 💡 顺带也验证了**纪律 2（看 min 不看 mean）**：3 号核有一趟测出 1761.0
> （另两趟 1368.2 / 1361.3），取 min 得 1361.3，离群值被正确滤掉。
> 若取 mean 会得到 1496.8，凭空多出 10%。

**② `cuda-compat` 的启用规则推不出来，只能实测**

本机状态：

```
LD_LIBRARY_PATH 含:  /usr/local/cuda/compat/lib              ← 该目录不存在
实际存在:            /usr/local/cuda/compat/lib.real/libcuda.so.615.71.09   ← 已禁用
实际加载:            /lib/x86_64-linux-gnu/libcuda.so.1 → libcuda.so.615.44
```

宿主机注入的是 **615.44**，compat 是**更新的 615.71.09**，compat **仍然**被禁用。
这与项目报告里「宿主机驱动比 compat 新时才禁用」的说法**不符**。

⇒ **版本高低推不出加载结果。** 详见 `../诊断手册.md` 纪律 3。

## host-裸机-20261030-仅环境采集

**同一台物理机，容器外直接跑 `run_all.sh`。未产出测量数据，但环境采集成功。**

### 为什么没跑成

```
############ 2/6 编译发射基准 ############
❌ 没有 nvcc，发射基准无法编译。请在带 CUDA toolkit 的环境中运行。
```

宿主机上没有 CUDA toolkit，T1 / T2 / T6 都需要现场编译，因此全部跳过。

> 🔧 **这次暴露了套件的一个真问题，已修复**：旧版 `run_all.sh` 在什么都没编译出来的情况下，
> 结尾仍旧打印「全部完成。请回传这一个文件」，**容易让人以为拿到了数据**。
> 现已改为：没有产出 `*_run1.csv` 时打印明确的失败块、给出可行替代路径、并以 `exit 1` 返回。
> 原脚本留存为 `../run_all.sh.orig-20261030`。

### 即便有 nvcc 也不该在这台上测

环境采集的「占卡进程（应为空）」一段**实测为非空**：

```
2590111, sglang::scheduler_TP0, 46722 MiB
2590112, sglang::scheduler_TP1, 46722 MiB
```

两张卡各被占用 46.7 GB。**机器不空闲，任何基准数据都不可用**——
这正是 `collect_env.sh` 设这一段的理由，它在本次确实拦住了一组会被误读的数据。

### 容器 vs 裸机的环境差异（这次唯一拿到的对比数据）

| 项 | 容器内 | 裸机 | 说明 |
| --- | --- | --- | --- |
| `nvcc` | 13.4 (V13.4.59) | **无** | 决定了能跑哪几台 |
| `perf_event_paranoid` | **4** | **3** | ★ **裸机反而能读 PMC** ★ |
| `CapBnd` | `a82425fb`（裁剪过） | `1ffffffffff`（完整） | 容器能力被裁剪 |
| `Seccomp` | `2` | 无 | 容器有 seccomp 过滤 |
| `LD_LIBRARY_PATH` | 含 torch / cuda compat 等 5 项 | **未设置** | |
| `cuda-compat` | 存在但为 `lib.real`（已禁用） | **完全不存在** | |
| **实际加载的 libcuda** | **615.44** | **615.44** | ★ **两边同一个 UMD** ★ |
| 时钟源 | tsc | tsc | 一致 |
| `systemd-detect-virt` | `n/a` | `none` | 容器内探测不到 |
| glibc | 2.39-0ubuntu8.9 | 2.39-0ubuntu8.8 | 镜像比宿主机略新 |

**两条可直接用的结论**：

1. **两边加载的是同一个 UMD（615.44）** —— 所以将来真做容器 vs 裸机对比时，
   差异只可能来自容器运行时本身（seccomp / cgroup / 能力裁剪），不是驱动。
2. **要指令数（T3/T4/T5）时，裸机比容器更顺** —— 裸机 `paranoid=3` 且能力完整，
   开箱即可读 PMC；容器则需要在**创建时**加 `--cap-add=PERFMON --user 0`。
   而 **T5（`run_perf_bugs.sh`）不需要 nvcc**，只依赖 `libcuda.so.1`，
   是没有 toolkit 的裸机上唯一能跑的测试台。

## 两条使用这些基线时的提醒

1. **`nvref-...` 这组数据是用修复前的 `run_all.sh` 跑的**（修复内容见上一节）。
   修复只改了「结尾怎么打印」和「失败时的退出码」，**不触碰任何测量逻辑**，
   所以数据仍然有效。原脚本留存为 `../run_all.sh.orig-20261030`。

2. **`±4%` 是同机重跑的本底漂移**，由这次 5 周后的复现实测得出。
   比较两台机器时，小于 ±4% 的差异不值得追。
