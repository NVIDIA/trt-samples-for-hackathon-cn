> 来源：2026-09 ~ 2026-10「RTX PRO 5000 vs L20 发射开销」内部调查（已结项）。

## 零、这套设备的适用范围

**它只测一件事：CPU 把一个 kernel 发射到 GPU 要花多少代价。**

被测 kernel 一律是 `__global__ void empty_kernel() {}`——GPU 侧计算被完全去掉，
剩下的就是纯发射开销。所以：

| 适合用它查 | 不适合用它查 |
| --- | --- |
| 推理 QPS 低，但 GPU 利用率也不高 | GPU 算力/显存带宽瓶颈 |
| 换驱动 / 换 GPU / 换 CPU 后性能倒退 | kernel 本身写得慢 |
| 虚拟机比裸金属慢 | 多卡通信（NCCL）问题 |
| 小 kernel 密集的模型（推荐类精排、小 batch LLM decode） | 大 kernel 为主的模型（发射开销占比极低） |

**一句话判据**：如果你的模型一次前向要发射几百上千个小 kernel，
那么「每次发射多付 300 ns」乘以 700 次 = 0.21 ms，在 2 ms 的前向里就是 10%。
反之如果一次前向只有几十个大 kernel，这套设备测出的差异对你没有意义。

### 为什么要分这么多测项

发射开销不是一个数，它至少是**五个维度**的函数，而真实业务只落在其中一个工作点上：

| 维度 | 由哪个测项覆盖 | 为什么不能只测一个点 |
| --- | --- | --- |
| **同步粒度**（每次同步 / 从不同步） | `1` `1b` `2` `3` `8a` | 580 驱动的退化只在深队列显现：浅队列 +5%，深队列 +47% |
| **队列深度** | `run_queue_depth.sh` | 同上，这是唯一能把「驱动是否有背压缺陷」问出来的扫描 |
| **是否走 Graph** | `4a-4c` `9a-9c` | Graph 把 N 次发射压成 1 次，正好绕开按次计费的开销 |
| **CPU 核的位置** | `percore_scan.sh` | 双路机上跨 NUMA 每次多付 11~13% |
| **哪张卡 / 几张卡** | `gpu_slot_scan.sh` | 本质也是 NUMA：远端 PCIe 槽位上的卡会慢 17% |

> ⚠️ **本套件最核心的方法论**：
> **时间这一个维度问不出更多东西的时候，改问指令数。**
> 指令数与 CPU 主频无关，于是把「同一段代码跑得慢」和「跑了不同的代码」一刀切开：
>
> | 现象 | 结论 |
> | --- | --- |
> | 指令数相同、耗时更长 | 同一段驱动代码，慢在 CPU / 内存子系统（频率、cache、TLB、MMIO 被 trap） |
> | 指令数更多 | 驱动**走了不同的代码路径**（版本差异、fallback 分支、额外检查） |
>
> 本项目正是靠这一招，把 299 ns 的残差拆成「驱动代际 211 ns + GPU 架构 98 ns」，
> 并证明 IPC 两边相同（1.472 vs 1.482）⇒ 不是 CPU 执行效率、不是虚拟化、不是硬件缺陷。

## 二、三条测量纪律（违反任意一条都会得到错误结论）

这三条不是建议，是本项目实际踩出来的坑。

### 纪律 1：CPU 预热，并丢弃第一次运行

`powersave` / `ondemand` governor 下，空闲后的第一个 CUDA 进程实测虚高 **23% ~ 105%**
（最极端一次 1684 ns vs 1366 ns，同机同卡）。

所有脚本都已内置「先在目标核上空转数秒 + 空跑一次丢弃」。
**但分析多次运行的结果时仍请丢弃 run1。**

### 纪律 2：看 min / p50，绝不看 mean

别的进程抢占只会让结果**变慢**，不会变快。所以：

- **min** 是最接近真值的估计
- **mean** 会被离群值污染——我们见过单次 0.88 **毫秒**的调度打嗝混进 10 万次采样

脚本结尾的自检若打印 `⚠️ 波动超过 10%`，说明测量期间机器上有别的负载，
**这种数据不能用来比较配置**，换个时间重跑。

### 纪律 3：核对**实际加载**的 `libcuda`

容器里经常同时存在两个用户态驱动（UMD）：

- `nvidia-container-toolkit` 从宿主机注入的
- CUDA 镜像自带 `cuda-compat` 包提供的

**我们自己就因此把「580 的测量」做成了「610 的测量」。**

> 🔥 最阴的一个坑：`compat/lib` 可能被改名成 `compat/lib.real` 从而被禁用，
> 而 `LD_LIBRARY_PATH` 里**仍然留着那个已经不存在的 `compat/lib` 路径**。
> **所以「目录在 `LD_LIBRARY_PATH` 里」和「它真的被加载了」完全是两回事**，
> 必须确认进程实际加载了哪一个。
>
> ⚠️ **什么时候会被禁用，不要靠猜。** 项目报告里曾总结为
> 「宿主机驱动**比** compat 包**新**时会被禁用」，但 **2026-10-30 在 本地实验室的参考机上
> 观察到一个反例**：宿主机注入 `615.44`、compat 是**更新的** `615.71.09`，
> compat **照样**是 `lib.real` 状态（被禁用），实际加载的是 `615.44`。
> 见 `baselines/nvref-pro5000-615.44-xeon-w5-3425_20261030/01_env.txt`。
>
> ⇒ **版本高低推不出加载结果，只能看实测。**
> 这反而强化了本条纪律：别推理，去读 `collect_env.sh` 的
> 「★实际会被加载的 libcuda★」段，或探针自报的 UMD。

探针会自报实际加载项（`run_queue_depth.sh` / `run_launch_pmu.sh` 的 `env.txt` 里
`### ★实际加载的 UMD（权威）★` 一段）。测老驱动时务必加 `NOCOMPAT=1`：

```bash
NOCOMPAT=1 bash run_queue_depth.sh <标签>-host    # 强制用宿主机注入的 UMD
bash run_queue_depth.sh <标签>-compat             # 用 compat 的 UMD
```

这两条命令构成一组**除 UMD 外完全无差异**的对照——同机、同容器、同核、同内核驱动。
本项目最干净的那个证明就是这么拿到的。

## 三、T0　环境采集（`collect_env.sh`）

**全程只读，不修改任何系统配置。** 10 秒跑完，但它决定了后面所有数字能不能解释。

| 采集段 | 关键项 | 预期 | 偏差说明什么 |
| --- | --- | --- | --- |
| 基本标识 | hostname / `uname -r` / 时间 | — | 用于对齐多台机器的数据 |
| **虚拟化与容器** | `systemd-detect-virt`、`/proc/cpuinfo` 的 `hypervisor` flag | 裸金属应为 `none` / 无 flag | 有 flag ⇒ 虚拟机，`timer` 与主频项的读法要换（见下） |
| **★ 时钟源 ★** | `current_clocksource` | 裸金属 `tsc` | **`kvm-clock` ⇒ `timer` 基线会从 ~15 ns 抬到 ~27 ns**，并连带抬高所有 `steady_clock` 计时（`issue`、`wall`）。此时 `timer` 一列**不可**跨机器比较 |
| CPU | `Model name`、`scaling_driver`、`scaling_governor`、`cpu MHz` | 裸金属有 cpufreq；governor 最好是 `performance` | `scaling_driver: n/a` ⇒ 虚拟机里**没有 cpufreq 子系统**，`/proc/cpuinfo` 的 `cpu MHz` 是标称值常数，**不反映实际 boost，不可信**。请改用 T4 的「隐含频率」 |
| C-state | idle driver 与各 state 的 latency | — | 深 C-state 会拉长每次 MMIO 的唤醒延迟；若 `percore` 结果离散度异常大，查这里 |
| **NUMA** | `numactl -H`、GPU 的 `numa_node` / `local_cpulist` | 单路机器 node=0 或 -1 | **多 NUMA 节点 ⇒ 必须确认进程绑在 GPU 本地节点**，否则主指标系统性虚高 11~13% |
| GPU | `nvidia-smi` 的 index/name/**driver_version**/persistence_mode/当前频率 | — | **driver_version 是 KMD（内核驱动）版本，不等于实际加载的 UMD** —— 见纪律 3 |
| CUDA | **`libcuda` 的实际解析路径与版本**、`compat/` 目录状态 | — | ★本套件最关键的一项★ 见纪律 3 |
| IOMMU 与内核参数 | `/proc/cmdline` | — | `iommu=pt` 之类会影响 MMIO 路径 |
| 系统负载 | `uptime`、`nvidia-smi` 进程列表 | 空闲 | 有别的负载 ⇒ 本次数据作废 |

> **读环境文件的顺序**：时钟源 → CPU 型号与 governor → NUMA 拓扑 → KMD 版本 → 实际加载的 UMD。
> 前四项定「这些数字该怎么读」，第五项定「这次到底测的是谁」。

## 四、T1　完整发射基准（`measure_launch.sh` → `kernel_launch_bench_split.cu`）

跑 4 趟（丢弃 run1），每趟输出 **41 行**测项。三种基本测法贯穿全表：

| 测法 | 代码形态 | 得到什么 |
| --- | --- | --- |
| **API only** | `t0; launch(); t1;` 不同步 | 单次调用的**提交**成本 |
| **+ sync** | `t0; launch(); sync(); t1;` | 单次**往返**延迟（含 GPU 执行与完成通知） |
| **throughput**（后缀 `.t`） | `t0; for(N) launch(); sync(); t1;` ÷ N | **稳态吞吐**，队列被填满（N 默认 10 万） |

下表的「参考」列取自 **本地实验室 RTX PRO 5000 48G / driver 615.x / Xeon w5-3425 / 单 NUMA 裸金属**，
这是本项目中**最干净的一台健康机器**，可当作「发射路径正常」的样板。
完整基线见 `基线参考值.md`。

### 4.0 基线测项

| 测项 | 做法 | 目的 | 参考 (ns) | **偏差诊断** |
| --- | --- | --- | --- | --- |
| `timer` | 连续两次 `Clock::now()` | 主机时钟读取开销，所有计时的本底 | **15** | **> 25 ⇒ 时钟源不是 `tsc`**（虚拟机 `kvm-clock` 实测 26.5~27.8）。此时全表的绝对值都被抬高，只能同机对比，不能跨机比。<br>**> 50 ⇒ 时钟源异常**（`hpet`/`acpi_pm`），先修时钟源再测 |

> ⚠️ 九月曾用 `测项/timer` 做跨机器归一化，后来**废弃**了：
> 单标量归一化会把多个不同成因的因素一起除掉，制造出"差异消失了"的假象。
> **跨机器比较请改用指令数（T4/T5），那是与频率无关的量。**

### 4.1　测项 1~3：基本发射

| 测项 | 做法 | 目的 | 参考 (ns) | **偏差诊断** |
| --- | --- | --- | --- | --- |
| `1` | `launch(); cudaDeviceSynchronize();` 每次都同步 | 最保守的往返口径（设备级同步最重） | **5171** | 与 `1b` 差距 > 5% ⇒ 设备级同步有额外成本，多卡场景值得查 |
| `1b` | `launch(); cudaStreamSynchronize();` | 流级同步的往返。**与 `4a` 同步范围对齐**，便于和 Graph 比 | **5164** | `1b` 正常但 `4a` 明显更高 ⇒ Graph 路径本身有问题 |
| `2` | `launch();` 不同步 | **纯提交成本**：把命令塞进队列要多久 | **1373** | 这是最常引用的「单次发射开销」。与 `8a` 差距 > 10% ⇒ 浅/深队列行为不一致，**立即跑 T3** |
| `3` | 连发 10 万次，末尾同步一次 | **背靠背吞吐**，深队列工作点 | **1341** | 应与 `8a` 基本相等（`8a` 只是显式指定了 stream）。两者差 > 5% ⇒ 测量噪声，重跑 |

### 4.2　测项 4：CUDA Graph（单节点）

| 测项 | 做法 | 目的 | 参考 (ns) | **偏差诊断** |
| --- | --- | --- | --- | --- |
| `4a` | `cudaGraphLaunch(); streamSync();` | Graph replay 的往返延迟，**对照 `1b`** | **4853** | 比 `1b` 低得有限（本例省 6%）——这是正常的 |
| `4b` | `cudaGraphLaunch();` 不同步 | Graph replay 的纯提交成本，**对照 `2`** | **2020** | **比 `2` 更高是正常的**（Blackwell 上 2020 vs 1373） |
| `4c` | 连发 10 万次 replay，末尾同步 | 单节点 Graph 的吞吐上限 | **2042** | — |

> ⚠️ **单节点 Graph 省不了多少，甚至更贵**——一次 replay 仍是一次主机↔GPU 往返。
> 本项目实测 Blackwell 上 `4c` / `9b(nodes=1)` 约 **1900~2040 ns**，是**架构固有的往返代价**。
> **看到这个数不要以为「Graph 没用」**，Graph 的价值在多节点摊薄，见 `9c`。

### 4.3　测项 5：GPU 时间轴

| 测项 | 做法 | 目的 | 参考 (ns) | **偏差诊断** |
| --- | --- | --- | --- | --- |
| `5` | `eventRecord(begin); launch(); eventRecord(end);` 同步后读 elapsed | **GPU 侧看到的区间** | **2400** | **两台机器的 `5` 接近而总耗时差很多 ⇒ 差距不在 GPU 侧**（本项目正是如此）。<br>反之 `5` 明显不同 ⇒ 查 GPU 频率、ECC、持久化模式 |

> ⚠️ `5` **不是「纯 kernel 执行时间」**：它含 GPU 时间轴上的空隙，也受 event 分辨率限制。
> 当成「GPU 侧的上界」来读。

### 4.4　测项 6：Cluster launch（**已证伪的方向，保留作模板**）

| 测项 | 做法 | 目的 | 参考 (ns) |
| --- | --- | --- | --- |
| `6a` | `cudaLaunchKernelEx`，`<<<8,32>>>` + cluster=2 | cluster 版发射的提交成本 | 1360 |
| `6b` | `6a` + 流同步 | cluster 版的往返 | 5165 |
| `6c` | 普通 `<<<8,32>>>` | `6a` 的基础对照 | 1377 |
| **`6d`** | **同样用 Ex API 但不开 cluster** | **关键对照**：把「Ex API 本身的开销」与「cluster 特性的开销」分开 | **1339** |
| `6e` | `6d` + 流同步 | | 5136 |

**偏差诊断**：

- `6a` ≈ `6d`（本例 1360 vs 1339，差 1.6%）⇒ **cluster 特性本身不额外收费**，九月对 Blackwell cluster launch 的怀疑被**证伪**
- `6a` 明显 > `6d` ⇒ cluster 真的有额外开销
- `6d` 明显 > `6c` ⇒ 贵的是 **Ex API 这层包装**，与 cluster 无关

> 💡 **这组测项的价值不在结论，在手法**：怀疑「特性 X 慢」时，
> 一定要造一个「同一个 API、只差开不开 X」的对照（`6a` vs `6d`），
> 否则你测到的是 API 差异而不是特性差异。**这个坑踩起来毫无感觉。**

### 4.5　测项 7：参数大小的影响

| 测项 | 做法 | 参考 API / 吞吐 (ns) | **偏差诊断** |
| --- | --- | --- | --- |
| `7a` / `7a.t` | 无参数 kernel | 1358 / 1358 | 基准 |
| `7b` / `7b.t` | **256 字节**参数 | 1451 / 1422 | 比 `7a` 高 ~90 ns（+6.8%） |
| `7c` / `7c.t` | **1024 字节**参数 | 1522 / 1463 | 比 `7a` 高 ~160 ns（+12%） |

**偏差诊断**：参数拷贝量确实收费，但**斜率很缓**（1 KB 才 +12%）。

- 若你的机器上 `7c` 比 `7a` 高出 **50% 以上** ⇒ 参数拷贝路径异常，查驱动版本
- 本项目中参数大小**不是主因**（真实模型的 kernel 参数远小于 1 KB）

### 4.6　测项 8：多流（★ 本项目主指标 ★）

| 测项 | 做法 | 目的 | 参考 (ns) | **偏差诊断** |
| --- | --- | --- | --- | --- |
| **`8a`** | **1 个 stream** 连发 10 万次，末尾同步一次 | **全项目引用最多的指标**。队列深度最贴近真实推理（一次前向连发 620~750 个 kernel 中间不同步） | **1337** | 见下 |
| `8b` | **8 个 stream** 轮流发，末尾各自同步 | 多流能否摊薄发射开销 | **1382** | `8b` 明显低于 `8a` ⇒ 单流存在串行瓶颈，多流可缓解；本例 `8b` 略高于 `8a` ⇒ **多流在此无收益**，别白费力气 |

**`8a` 的偏差诊断（这是整套设备最重要的一个数）**：

| `8a` 观察到的值 | 可能的问题 |
| --- | --- |
| **≈ `2`（API only）** | 正常。浅深队列行为一致 |
| **明显 > `2`（> +15%）** | ★ **驱动在深队列下劣化** ★ —— 580 分支的典型特征。**立即跑 T3 确认**，并查实际加载的 UMD 版本 |
| **两台机器的 `8a` 逐位吻合** | 强证据：差异来自**两边共有的东西**（本项目中 远端环境与 本地实验室在 580 上测出 2047.1 / 2046.9，直接锁定「根因是 580 驱动」而非机器环境） |
| **比参考值高 10~20% 且 `percore` 有分层** | 跨 NUMA，见 T6 |
| **比参考值高 ~2 倍且只有第一次** | 没预热，违反纪律 1 |

### 4.7　测项 9：CUDA Graph 节点数扫描（★ 优化建议的依据 ★）

对 **nodes ∈ {1, 8, 32}** 各跑一组，共 9 行。

| 测项 | 做法 | 目的 | 参考 n=1 / n=8 / n=32 (ns) |
| --- | --- | --- | --- |
| `9a` | `cudaGraphLaunch();` 不同步 | Graph 的纯提交成本 | 2022 / 4077 / 14390 |
| `9b` | 连发 10 万次 replay，末尾同步 | 整个 Graph 的 replay 吞吐 | 2029 / 4098 / 14894 |
| **`9c`** | **`9b ÷ nodes`** | **摊薄到每个 kernel**：把 N 个 kernel 打进一个 Graph 能省多少 | **2029 / 512 / 465** |

**怎么读**：`9c` 从 2029 → 512 → 465，说明

1. 节点越多摊薄越明显，但**收益很快饱和**（8→32 只再省 9%）
2. 对照 `8a` = 1337：**8 节点的 Graph 已经把每 kernel 成本降到 38%**

**偏差诊断**：

| 观察 | 说明 |
| --- | --- |
| `9c(n=8)` ≈ `9c(n=1)` | Graph 没有真正批量化，查 Graph 是否被 capture 成了多次提交 |
| `9c(n=8)` 高于参考值但 `8a` 正常 | Graph 路径单独有问题（驱动 bug 或 Graph 太复杂） |
| `9c` 远低于对手而 `8a` 远高于对手 | ★ **典型的「该上 Graph」信号** ★ ——本项目正是：eager 路径 Pro5000 慢，Graph 路径反超 23~26% |

> ⚠️ **`9c` 是推导值（`9b ÷ nodes`）**，不是单个 kernel 的真实延迟，也不是节点之间的间隙。
> 别拿它跟 `2` 直接比「单次发射」。

### 4.8　测项 10：launch 形状与 shared memory

执行顺序是 **a → b → d → e → c**（`10c` 需先做 opt-in 检查，故放最后）。

| 测项 | 形状 `<<<grid, block, smem>>>` | 作用 | 参考 API / 吞吐 (ns) |
| --- | --- | --- | --- |
| `10a` / `10a.t` | `<<<1, 1, 0>>>` | 最小形状，基准 | 1345 / 1338 |
| `10b` / `10b.t` | `<<<8, 32, 0>>>` | 典型形状 | 1346 / 1332 |
| `10d` / `10d.t` | `<<<1, 32, 0>>>` | **控制变量**：block 数固定为 1，只变每 block 线程数 | 1349 / 1336 |
| `10e` / `10e.t` | `<<<8, 1, 0>>>` | **控制变量**：每 block 1 线程，只变 block 数 | 1343 / 1333 |
| `10c` / `10c.t` | `<<<8, 32, 48 KiB>>>` | **动态 shared memory** 对发射成本的影响 | 1360 / 1334 |

**偏差诊断**：参考机上五者差异 **< 1.5%** ⇒ **发射形状基本不收费**，这是正常的。

- 若 `10c` 显著高于 `10b`（> 10%）⇒ 动态 shared memory 的 opt-in 路径有额外成本
- 若 `10e` 随 block 数明显上升而 `10d` 不变 ⇒ 成本与 **block 数**相关（命令描述符按 block 构造）
- 反之 ⇒ 成本与**每 block 线程数**相关

> 💡 `10b` / `10d` / `10e` 三者配合才能把 **block 数**与**每 block 线程数**的影响分开，
> 这是单看 `10a` vs `10b` 做不到的。
>
> `10c` 需要 48 KiB 动态 shared memory。超出设备上限或 opt-in 不被支持时，
> 该项会标记为 **SKIP** 并给出原因，**而不是静默失败**——这是刻意的设计，
> SKIP 行也会写进 CSV，免得分析时把「没测」当成「测了没问题」。

## 五、T2　往返拆分（`run_roundtrip.sh` → `launch_roundtrip.cu`）

T1 的测项 `5` 只量 GPU 时间轴区间，**看不到命令提交延迟和完成通知延迟**。
本测试台在同一轮外面再套一层 `steady_clock`，把这两部分分开。

### 5.1　第一部分：一次往返的三段拆分

```
wall  = 整轮墙钟（提交 3 条命令 + 等完成通知）
event = GPU 时间轴上 begin event -> end event 的区间
host  = wall - event   ← 不在 GPU 时间轴上的主机侧开销
```

| 指标 | 目的 | 参考（远端环境 Pro5000 @615） | 参考（远端环境 L20 @535） | **偏差诊断** |
| --- | --- | --- | --- | --- |
| `wall` | 单次往返总延迟 | **6970** | **8050** | — |
| `event` | GPU 侧区间 | **2720** | **2784** | **两边差 ≤ 2% ⇒ GPU 侧无辜**（本项目实测差 2.3%）。差异大 ⇒ 查 GPU 频率/ECC/持久化 |
| `host` | 提交延迟 + 完成通知延迟 | **4266** | **5264** | ★ **每轮只付一次**，不随 N 增长 ★。两边差 ≤ 1% ⇒ 提交/通知路径无差异（本项目 0.4%） |

> ⚠️ 这是「一次一停」模式，每轮都会把流水线排空，衡量的是**单次往返延迟**，
> **不能**与背靠背发射的摊薄成本（`8a`）直接比较。

### 5.2　第二部分：纯 CPU 发射成本的 N 扫描

```
cudaStreamSynchronize(s);                   // 先清空此前的工作
t0; for (N 次) empty_kernel<<<>>>(); t1;    // 只发射，不等
cudaStreamSynchronize(s);  t2;              // 排空

issue = (t1-t0)/N      每次发射的 CPU 成本
drain = (t2-t1)        发射完之后还要等多久排空
```

扫描 N ∈ {1, 4, 16, 64, 256, 1024, 4096, 16384, 65536}。

| N | 参考 issue（远端 Pro5000） | 参考 issue（远端 L20） |
| --- | --- | --- |
| 1 | 1593 | 1330 |
| 16 | 1670 | 1366 |
| 64 | 1675 | 1367 |
| 256 | 1678 | 1371 |
| 1024 | **1684** | **1368** |

**偏差诊断**：

| 观察 | 结论 |
| --- | --- |
| `issue` 随 N 基本持平（本例 ±1%） | ✅ 正常。该列**确实**代表纯 CPU 发射成本 |
| **`issue` 随 N 明显上升** | ❌ **已撞到队列背压**——CPU 被阻塞在等队列腾空，该列**不再代表 CPU 成本**，而是退化成 GPU 的排空速率。此时请改看小 N（16~256）的值 |
| 各趟之间 `host` 波动 > 10% | 测量期间有别的负载，脚本会打印 `⚠️`，重跑 |

> 💡 **`host` 和 `issue` 构成一个可直接套用的成本模型**：
>
> ```
> 一次前向（N 次发射 + 1 次同步）≈ N × issue + host
> ```
>
> 本项目用它算出了 Pro5000 与 L20 的**持平点**：
>
> ```
> Pro5000 = N × 1691 + 4266
> L20     = N × 1368 + 5264
> 持平点 N = (5264 − 4266) / (1691 − 1368) ≈ 3
> ```
>
> N ≤ 3 时 Pro5000 更快（主机侧开销低 999 ns）；N 很大时 L20 占优。
> **CUDA Graph 等效于把 N 拉回 1**，正好落回 Pro5000 占优的区间。
> ——这个两参数模型是整个项目里最有用的一个推导，**它把「谁更快」变成了「N 多大」**。

## 六、T3　队列深度扫描（`run_queue_depth.sh`）★ 本项目的根因就靠它 ★

**回答一个问题：这个驱动在深队列下是否会劣化。**

### 6.1　为什么必须单独扫

580 分支的发射退化**只在队列深的时候显现**：

| 每多少次同步一次 | 580 比 615 慢 |
| --- | --- |
| 64 | +5.0% |
| 256 | +12.1% |
| 1024 | +16.0% |
| 8192 | +34.3% |
| 65536 | +40.8% |
| **10 万次连发后同步** | **+47.4%** |

真实推理每次前向连发几百上千个 kernel 且中间不同步，**正好落在最糟的工作点**。

> 🔥 **这解释了为什么微基准和真实业务的结论差那么多。**
> 用「每几百次就同步一次」的微基准去测 580，会把影响**低估到 5~16%**，
> 从而得出「驱动没问题」的错误结论。
> **评估驱动影响时，必须用贴近真实负载的队列深度。**

### 6.2　脚本做两件事

| 段 | 做法 | 产出 |
| --- | --- | --- |
| **[A] 8a 基准** | 10 万次背靠背 + 末尾一次同步（与历史数据同口径） | `a8.txt`、p50 中位 |
| **[B] BATCH 扫描** | 用 PMU 两点差分，测每个队列深度下的**指令数 / 周期数 / 耗时 / IPC / GHz** | `sweep.txt` |

两者应当对上：`BATCH=100000` 的结果 ≈ `8a`。脚本会自动做这个交叉验证，
**差 < 7% 打 ✅，否则打 ⚠️**。

### 6.3　判读表

| 观察 | 结论 |
| --- | --- |
| 浅→深 耗时变化在 **±2%** 内 | ✅ 该驱动在深队列下正常（**610 / 615 分支的表现**：−0.7% / +1.9%） |
| 浅→深 耗时**显著上涨**（本例 +29%） | ❌ 该驱动的**背压/提交路径有问题**（580 分支的典型特征） |
| **耗时与指令数同时上涨** | ★ 最强的证据 ★ —— 不是「CPU 在等」，而是驱动**真的多执行了指令**（580 实测指令数也涨 15.1%），指向提交路径里有**重试/自旋循环**，队列越满转的圈越多 |
| 耗时涨但指令数持平 | CPU 在等队列腾空（背压），属正常饱和，不是驱动缺陷 |
| 交叉验证打 `⚠️`（两套工具差 > 7%） | 测量被打断，或 `8a` 解析失败，重跑 |

参考数据（本地实验室 Pro5000，同机只换驱动）：

| 256 | 10257.9 | 9540.1 | 9249.0 |

## 七、T4　PMU 两点差分（`run_launch_pmu.sh`）

**任何驱动版本都能跑**（T5 的 `perf_bugs` 需要 driver ≥ 570），不需要 root、不需要改驱动。
纯源码约 10 KB，目标机现场编译。

### 7.1　原理

用 `freq_monitor`（PMU 采集器）包住探针，分别发射 `T1` 和 `T2` 次，两点差分：

```
每次 launch 的指令数 = (指令_T2 − 指令_T1) / (T2 − T1)
```

差分把 CUDA 初始化、建 context、预热等**固定开销全部消掉**。
探针按 1024 次一批同步，**避免队列填满后 CPU 被背压阻塞**（那会把指令数也带偏）。

### 7.2　五个输出及其诊断

| 指标 | 目的 | 参考（本地 Pro5000 / 615.71.09 / Xeon w5-3425） | **偏差诊断** |
| --- | --- | --- | --- |
| **指令数** | ★与主频无关★，用于区分「同一段代码」与「不同代码路径」 | **9081 条** | 见下方专表 |
| 周期数 | | 5622 | — |
| 耗时 | 每次 launch | **1389 ns** | 与 T5 的 1367 ns 交叉验证，差 1.6% ⇒ 两套独立实现一致 |
| **IPC** | 指令数 / 周期数 | **1.615** | **两台机器 IPC 相同 ⇒ 差距全部来自指令数**，不是 CPU 执行效率、不是虚拟化、不是硬件缺陷（本项目 1.472 vs 1.482，差 0.7%） |
| **隐含频率** | 周期数 / 耗时 = 发射循环期间 CPU 的**实际**运行频率 | **4.05 GHz** | ★虚拟机里 `/proc/cpuinfo` 的 `cpu MHz` 是标称值常数，以这个为准★。本项目实测：VM 报 2596 MHz，实际睿频 **3.678 GHz** |

**指令数的判读**：

| 观察 | 结论 |
| --- | --- |
| 指令数相同、耗时更长 | 同一段驱动代码，慢在 **CPU / 内存子系统**（频率、cache miss、TLB、MMIO 被 trap） |
| 指令数更多 | 驱动**走了不同的代码路径**（版本差异、fallback 分支、额外检查） |

### 7.3　内置护栏

脚本会自检**隐含频率**是否落在 `0.5 ~ 6.0 GHz`：

```
❌ 隐含频率 X GHz 不合理（正常应在 0.5~6 GHz）。本组数据不可用。
```

> 💡 **为什么用隐含频率做自检**：它是三个独立测量值算出来的（指令数、周期数、耗时），
> 任何一项解析出错或测量被打断，它都会立刻离谱。
> 而真实 CPU 不可能跑在这个区间外。
> **所以它是整组数据最灵敏的单点自检指标**——这是个值得抄走的设计。

IPC 落在 `0.2 ~ 6` 之外也会打 `⚠️`。

### 7.4　★ 口径限制（最容易出错的一条）★

> **本脚本的指令数不能与 `perf_bugs`（T5）的指令数直接比较。**
>
> 本脚本走 CUDA runtime API（`cudaLaunchKernel` → `cuLaunchKernel`），
> `perf_bugs` 直接调 driver API，中间差一层包装——**同机实测差约 792 条**。
>
> **跨机器比较时，所有机器统一用同一个工具。**

**重复性**：指令数的轮间波动约 **±0.5%**（差分法天然比 `perf_bugs` 的 ±0.01% 噪声大，
因为是两个大数相减）。要分辨的效应在 **5% 以上**时，这个精度够用。

## 八、T5　perf_bugs（`run_perf_bugs.sh`）

NVIDIA 内部的 CUDA 驱动微基准，与本套件自带的 `kernel_launch_bench` 是**两套独立实现**，
用于交叉验证。只链接 `libcuda.so.1`，**不需要装 CUDA Toolkit、不需要编译**。

**前置**：driver ≥ 570（它引用了 `cuCtxCreate_v4` 等较新 API）。老驱动请改用 T4。

### 8.1　测项与参考值

| 指标 | 目的 | 远端环境 Pro5000 @615.71.09 | 本地实验室 Pro5000 @615.44 |
| --- | --- | --- | --- |
| `cuLaunchKernel` 耗时 | 单次发射 | 1606~1622 ns | 1360~1390 ns |
| **`cuLaunchKernel` 指令数** | ★与主频无关★ | **8289 条** | **8334 条** |
| `mean_host_latency` | 主机侧延迟 | 1529~1548 ns | 1385 ns |
| `mean_total_latency` | 总延迟 | 3046~3144 ns | 3190 ns |
| `device_launch_latency` | 设备侧发射延迟 | 1517~1596 ns | 1800 ns |
| CPU 实测运行频率 | 稳态中位 | 3.68 GHz | 4.01~4.10 GHz |

**诊断示例（本项目实际用法）**：两边指令数 8289 vs 8334（差 0.5%），
但耗时差 17.5% ⇒ **同一段代码，差在 CPU**（频率 0.917× × IPC 0.922×）。
这直接排除了「驱动走了不同路径」的可能，把问题定位到 CPU 单线程性能差异。

### 8.2　脚本替 `perf_bugs` 补的两个坑

**请不要跳过脚本直接裸跑 `bin/perf_bugs`**，否则拿到的数会同时混进这两个误差：

| 坑 | 后果 | 脚本怎么处理 |
| --- | --- | --- |
| **它默认把自己钉在 0 号核上** | 0 号核通常在处理中断，且双路机上大概率与 GPU 不同 NUMA。实测跨 NUMA 多付 **200~410 ns**——**和我们要找的 300 ns 残差是同一个量级，会直接把结论带偏** | 用 `--dont-pin-threads` 解除自绑定，再用 `pick_core.sh` 选 GPU 本地节点的核 |
| **不做 CPU 预热，也不丢弃首轮** | 实测虚高 **23%**（1684 vs 1366 ns，同机同卡） | 先空转 4 秒拉满频率，丢弃一轮，再正式测 3 轮 |

### 8.3　怎么拿到指令数（三条路，任选其一）

| 路线 | 做法 | 适用 |
| --- | --- | --- |
| **0** | `sudo bash run_perf_bugs.sh <标签>` | 裸机 / 不用容器。root 默认持有 `CAP_PERFMON` |
| **A** | `docker run --cap-add=PERFMON --user 0 ...` | 容器，**不需要宿主机 sudo** |
| **B** | `sudo sysctl -w kernel.perf_event_paranoid=3` | 需要宿主机 sudo。只影响"非特权用户能否读性能计数器"，不改调度/内存/驱动行为 |
| **C** | 直接跑，只看时间 | 前三条都走不通时。会打印 `Failed to enable PMC to count instructions` |

> 🔥 **路线 A 的两个 flag 缺一不可**（实测踩出来的）：
> `--cap-add` 只把能力放进 bounding + permitted 集；容器内若以**非 root 用户**运行，
> permitted 实际为空，能力完全拿不到，`perf_event_open` 仍返回 `Permission denied`。
> 加上 `--user 0` 之后一次成功。
>
> ⚠️ 必须在**创建容器**时加，已经在跑的容器改不了（加到 `docker exec` 上**无效**）。
> docker 版本不认 `PERFMON`（需内核 5.8+）时改用 `--cap-add=SYS_ADMIN`。

### 8.4　容器内做 UMD A/B（强烈推荐，一分多钟）

```bash
bash run_perf_bugs.sh <标签>-compat            # A: 用 compat 的 UMD
NOCOMPAT=1 bash run_perf_bugs.sh <标签>-host   # B: 用宿主机注入的 UMD
```

`env.txt` 的 `### libcuda` 段会打印实际加载的 `libcuda.so.<版本号>`，可直接核对切换是否生效。
**两次版本号相同** ⇒ 该镜像没装 compat 包，这组对照做不了（只交 A 即可）。

## 九、T6　拓扑扫描（`percore_scan.sh` / `gpu_slot_scan.sh`）

### 9.1　逐核扫描

kernel launch 的最后一步是往 GPU doorbell 寄存器做 **MMIO 写**。
在多 CCD / 多 NUMA 的大核数 CPU 上，不同核到 IO die（PCIe 所在）的距离不同，
这一步的延迟可能**因核而异**。

```bash
./percore_scan.sh              # 默认每 8 个逻辑核取一个，再加 0~7
./percore_scan.sh --all        # 全扫（核多时慢）
./percore_scan.sh --step 4
```

每个核测 3 趟取 **min**，并按 `die_id` / `cluster_id` / NUMA node 分组。

| 观察 | 结论 |
| --- | --- |
| 全部核的极差 **< 9%** | ✅ 正常。本地实验室单 die 机器的噪声基线就是 **8.9%**（实测 1327~1442 ns） |
| 极差明显超过 9% 但**无明显分层** | 核的位置有影响（多 CCD），**绑核是一个可落地的优化** |
| ★ **出现清晰的两组平台，组内极紧（±1%）、组间断崖式跳变** ★ | **跨 NUMA**。边界会精确落在 NUMA 分界核上，**没有中间态** |
| 单个核波动 > 10%（脚本打 `⚠`） | 该核被抢占，复测 |

**实测参考（某双路 EPYC 机，GPU 在 node0）**：

| 核 | NUMA | min (ns) |
| --- | --- | --- |
| 0 ~ 48 | 0 | 1934 ~ 2041 |
| 56 ~ 96 | 1 | 2373 ~ 2420 |

差 **+18%**，边界精确落在 48/56 之间。另两台的实测：

| 机器 | node0（GPU 所在） | node1（远端） | 代价 |
| --- | --- | --- | --- |
| 双路 EPYC 9K65（VM） | 1755.5 | 1961.5 | **+206.0 ns（+11.7%）** |
| 双路 EPYC 9K65（裸金属） | 1714.8 | 1939.9 | **+225.1 ns（+13.1%）** |

> 🔥 **这是我们自己踩过的坑**：早期版本绑「允许集合里的**最后一个**核」，
> 在双路机上恰好选到远端节点，导致主指标系统性虚高 **12~14%**。
> 现在 `pick_core.sh` 会读 GPU 的 `numa_node` 与 `local_cpulist`，
> **只在 GPU 本地节点的核里选**，并打印选择理由。单 NUMA 机器行为不变。
>
> **生产部署同理 —— 把推理线程绑到 GPU 所在 NUMA 节点，白赚 11~13%。**
>
> ```bash
> cat /sys/bus/pci/devices/<GPU的PCI地址>/numa_node
> ```

### 9.2　槽位 / 可见设备数扫描

5 个配置，每个 3 趟取 min：

- `only_gpuN`：`CUDA_VISIBLE_DEVICES=N`，只暴露 1 张卡，逐张试（看 PCIe 槽位差异）
- `all_Ngpus_dev0`：不设 `CUDA_VISIBLE_DEVICES`，全部可见但用 device 0（看**设备数量**的影响）

| 观察 | 结论 |
| --- | --- |
| 各 `only_gpuN` 之间差 < 2% | ✅ 槽位无影响 |
| `all_*_dev0` ≈ `only_gpu0` | ✅ **可见设备数量无影响**（本项目实测 2030.4 vs 2031.0，差 0.03%） |
| ★ 部分卡明显更慢且**成组** ★ | **那组卡挂在远端 NUMA 节点上**——这其实是 9.1 的另一面 |

**实测参考（某 8 卡双路机，绑核在 node0）**：

| 配置 | min (ns) |
| --- | --- |
| only_gpu0 ~ gpu3 | 2023 ~ 2042 |
| **only_gpu4 ~ gpu7** | **2380 ~ 2393（+17%）** |
| all_8gpus_dev0 | 2030 |

GPU 4~7 挂在另一个 socket 上，而进程绑在 node0 ⇒ 每次发射多付约 350 ns。

> 💡 **这张表的部署含义比它的诊断含义更大**：
> 多卡机器上**不是每张卡都等价**。调度器如果只按显存空闲挑卡，
> 可能把延迟敏感的小 kernel 业务放到远端卡上，白白损失 17%。

## 十、T7　KVM 专项：doorbell MMIO 是否被 trap

**虚拟机比裸金属慢时，这是最直接的一项证据。**

kernel launch 的最后一步是 CPU 往 GPU doorbell 寄存器做一次 MMIO 写。
若这块 BAR 在 KVM 下被 trap，**每次 launch 都会产生一次 VM exit**，
正好能解释「每次发射多出固定开销」。

### 两边各跑一个程序

```bash
# ① 宿主机侧（需 root）
sudo bash kvm_mmio_host.sh --n 100000
# 它先快照计数器，提示你去虚拟机里跑，回车后再快照并给出增量与判读
# 也可以 --watch 持续采样

# ② 虚拟机侧
./mmio_probe 100000
# 只做一件事：精确发射 10 万次空 kernel，前后各留 3 秒静默窗口
```

### 判读

| `mmio_exits 增量 / N` | 结论 |
| --- | --- |
| **≈ 1**（0.8 ~ 1.5） | ★ **每次 launch 对应一次 MMIO exit —— doorbell 写确实被 KVM trap** ★ |
| **≈ 0**（< 0.1） | doorbell 写没被 trap，**KVM 在这条路径上无辜** |
| 介于两者之间 | 需结合 `exits` 总数判断（可能部分 trap，或有其它来源） |

脚本会自动算这个比值并给出判读。

### 注意事项

- **必须在宿主机上跑**，虚拟机里看不到 `/sys/kernel/debug/kvm/`
- 新内核下每个虚拟机有独立子目录（`<pid>-<n>/`），脚本会自动识别；
  **只有老内核的全局计数**才需要保证宿主机上只有被测虚拟机在活动（脚本会提示）
- debugfs 没挂载时脚本会尝试 `mount -t debugfs none /sys/kernel/debug`
- ⚠️ **这一项 本地实验室无法预先验证**（我们的机器是裸金属，没有 `/sys/kernel/debug/kvm`），
  脚本已尽量容错，遇到问题请把报错发回

> **本项目的结论**：虚拟化**被排除**。同配置裸金属 vs KVM 直通，
> 各项差异 ≤ 3%，真实模型 QPS 中位比 0.972。

## 十一、T8　真实模型 QPS（压测器需自备）

> ⚠️ **本测项的压测器已从本仓库移除。** 原来的 `run_qps.sh` / `bench/qps_bench.cpp` /
> `bench/CMakeLists.txt` 源自客户项目，不适合随这个公开仓库发布，已整体删除。
> 下面保留的是**方法与结论**，它们是调查过程换来的、与客户代码无关的部分。

### 这一项测什么

端到端业务指标：多线程 × 多 CUDA Stream 并发推理，扫 32 个工况
（batch 4~512 × threads 1/2/4/8），看 QPS（samples/s）与 P50/P99 延迟。
它与 T0~T7 完全解耦 —— 前面测的是"发射一个 kernel 要多少代价"，这一项回答
"这些代价在真实负载上折算成多少吞吐损失"。

要复现需要自己实现一个压测器，关键要素：共享或每线程独立的模型 loader、
线程池 + 显式传 stream、丢弃 warmup、按 min/P50 统计而非 mean。

### ★ 发现一：一个布尔参数默默关掉了整条优化路径 ★

```cpp
AOTIModelPackageLoader loader(aot_model_path, "model", /*run_single_threaded=*/false);
```

**这个 `false` 会阻碍 CUDA Graph。** `run_single_threaded=false` 时 AOTI 会在 `run()` 内部调用
`cudaEventQuery`，而该调用在 stream capture 期间非法，捕获直接失败。

> 💡 **值得学的一点**：这种「一个布尔参数默默关掉了整条优化路径」的情况，在
> AOTInductor / TorchInductor 这类有多层封装的栈里特别常见，而且**不会报错、不会警告，只是慢**。
> 排查时的有效手法是：**先用微基准确认硬件/驱动路径上 Graph 是有收益的（见 9c），
> 再回头质问为什么业务代码里没拿到这个收益** —— 顺序反过来会一直在业务代码里打转。

### ★ 发现二：给 AOTI 模型套 CUDA Graph 的四个前提 ★

这四条是实测踩出来的，任何人重新实现压测器时都会遇到：

1. **loader 必须用 `run_single_threaded=true` 构造**，否则 `run()` 里的 `cudaEventQuery`
   会让 stream capture 直接失败（即发现一）。
2. **光改那个开关不会提速**，必须真正做 capture + replay —— 改开关只是解除了阻碍。
3. **输入地址必须固定**：先 `clone()` 一份 static_inputs 留作固定缓冲，之后每次把新数据
   `copy_` 进去再 replay。graph 记录的是地址，不是值。
4. **每线程独立 loader + 独立 graph**：`run_single_threaded` 的实例不能跨线程共享。
   代价是每线程各持有一份权重，显存随线程数线性增长。

另外，**捕获前必须预热若干次**（实测 10 次足够），让 Triton kernel 完成惰性加载、
cuBLAS 分配好 workspace，否则捕获期间会触发非法调用。

```
│
├─ 1. 跑 T1，看 8a 与 2 ─────────────────────────────────────────────
│     ├─ 8a ≈ 2（差 < 10%）          → 浅深队列一致，跳到 ③

│
├─ 2. 跑 T2，看 event 与 host ──────────────────────────────────────
│     ├─ event 两边接近（≤2%）       → GPU 侧无辜，差距在 CPU 侧
│     ├─ host 两边接近（≤1%）        → 提交/完成通知路径无差异
│     └─ 用 N×issue + host 算持平点  → 得出「N 多大时谁更快」

│     ├─ 指令数相同、IPC 不同            → CPU/内存子系统（cache、TLB、MMIO trap）
│     └─ ★ 指令数不同 ★                  → 驱动走了不同代码路径

│

│     ├─ 出现两组平台、断崖式跳变   → 跨 NUMA，绑到 GPU 本地节点，白赚 11~13%

│
├─ 6.（仅虚拟机）跑 T7 ─────────────────────────────────────────────
│     └─ mmio_exits/N ≈ 1 → doorbell 被 trap；≈ 0 → KVM 无辜
│
└─ 7. 跑 T8 端到端复测 ─────────────────────────────────────────────
```

## 十三、这套设备能得出的结论类型（附证据等级）

**本设备不能告诉你「硬件坏了」。** 它能把差异归因到下面几个互斥的桶里：

| 结论桶 | 判据 | 能否消除 |
| --- | --- | --- |
| **驱动缺陷** | 同机同卡只换 UMD，指令数与耗时同时变化；深队列劣化 | ✅ 升级驱动，或容器走 cuda-compat |
| **驱动代际差异** | 同 GPU 换驱动版本，指令数不同 | ❌ 不是缺陷。新架构往往不被老驱动支持，没有「降级追平」这条路 |
| **GPU 架构差异** | 同驱动换 GPU，指令数不同 | ❌ 架构代差 |
| **CPU 单线程性能** | 指令数相同，频率 × IPC 解释全部差异 | ❌ 硬件选型取舍 |
| **NUMA / 拓扑** | 逐核扫描出现断崖式分层 | ✅ 绑核 |
| **KVM trap** | mmio_exits/N ≈ 1 | 取决于平台配置 |
| **测量方法错误** | 违反三条纪律之一 | ✅ 重测 |

### 本项目的最终归因（作为示范）

| # | 原因 | 量级 | 状态 |
| --- | --- | --- | --- |
| 1 | 驱动 580 分支的发射路径回归 | 发射开销 **+42~47%**（深队列） | ✅ 已解决（升级驱动） |
| 2 | 驱动代际差异（L20 停在 535，Pro5000 必须用 615） | **+211 ns / 次** | ⚠️ 无法消除 |
| 3 | GPU 架构差异（Blackwell 的命令构造比 Ada 复杂） | **+98 ns / 次** | ⚠️ 无法消除 |

**唯一有效的手段是 CUDA Graph**：它把 N 次发射压成 1 次，正好绕开这笔「按次计费」的开销。

### 证据等级怎么标

写结论时请一并标出等级，**这是本项目报告中最被认可的一点**：

| 等级 | 含义 | 本项目的例子 |
| --- | --- | --- |
| ✅ | 同机受控 A/B，多次复现 | 580 的回归及其队列深度特性 |
| ✅ | 同 CPU、同工具直接测量 | L20 vs Pro5000 总差 299 ns |
| ⚠️ | 依赖参照机作桥，精度有限 | 68% / 32% 的**拆分比例**（±5 个百分点） |

> 🔥 **并且要说明不确定性影不影响建议**。本项目：
> 「拆分比例的不确定性来自作为桥梁的参照机 CPU 较老（无 AVX-512），
> 若驱动按 CPU 特性分派，可能有偏差。
> **该不确定性不影响任何建议——无论比例如何，两项都不是配置能解决的。**」
>
> 把「我不确定的部分」和「这影响不影响你的决策」分开讲，
> 比假装全部确定更容易被接受，也比笼统说「仅供参考」有用得多。

## 十五、一页纸速查

```
跑之前   ── 机器空闲？governor=performance？知道 GPU 在哪个 NUMA 节点？
```
