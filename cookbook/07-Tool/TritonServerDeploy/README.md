# TritonServerDeploy

+ Deploy a TensorRT engine on Triton Inference Server, end to end.

Build the engine, lay out the model repository, start the server, send a request, compare the
answer against a local reference, shut the server down.

```bash
python3 main.py            # build + serve + query + clean up
python3 main.py --no-serve # only build the model repository
python3 test_client.py     # exercise the client half without a server (see below)
```

## What runs where

| Stage | Needs | In this container (`nvcr.io/nvidia/pytorch`) |
| ----- | ----- | -------------------------------------------- |
| 1. build engine + model repository | `tensorrt` | ✅ runs |
| 2. local reference inference | `tensorrt`, `cuda-python` | ✅ runs |
| 3. start server, query, compare | **`tritonserver` binary** | ✅ runs, after the no-docker install below |
| 4. teardown | — | part of stage 3 |

`tritonserver` ships only inside `nvcr.io/nvidia/tritonserver:<yy.mm>-py3`. The PyPI package of the
same name contains **only the Python bindings** (one `.so`, no `libtritonserver.so`, no backends),
so `pip install tritonserver` does not make this runnable — checked, not assumed.

Without a `tritonserver` binary in `PATH`, stage 3 prints what it would have run and returns
instead of failing. **But the binary can be had without docker and without root** — see
[Getting `tritonserver` without docker](#getting-tritonserver-without-docker-verified-here): with
it, all four stages run here and Triton's answer comes back bit-identical to the local TensorRT
reference.

`test_client.py` covers the same client code with no server at all, so the CI of a plain TensorRT
container still exercises it: it replaces Triton with a stub that speaks KServe v2 and checks the
request encoding, the response decoding, the readiness polling and the teardown. What it cannot
cover is whether Triton accepts `config.pbtxt`; the last case cross-checks the config against the
engine's own tensor shapes as a partial stand-in.

## The model repository

Triton discovers models by directory layout, and the layout is not negotiable:

```txt
model_repository/
└── mnist-cnn/                 <- the model name that appears in the URL
    ├── config.pbtxt
    └── 1/                     <- version, an integer directory
        └── model.plan         <- fixed file name for the `tensorrt_plan` platform
```

`config.pbtxt` as generated by `main.py`:

```txt
name: "mnist-cnn"
platform: "tensorrt_plan"
max_batch_size: 16
input [ { name: "x" data_type: TYPE_FP32 dims: [1, 28, 28] } ]
output [
  { name: "y" data_type: TYPE_FP32 dims: [10] },
  { name: "z" data_type: TYPE_INT64 dims: [1] reshape { shape: [] } }
]
instance_group [ { count: 1 kind: KIND_GPU } ]
```

Three things that bite here:

+ **`max_batch_size > 0` means Triton owns the first dimension**, so every `dims` is the shape of
  *one sample*: the engine's `x` is `(-1, 1, 28, 28)` and the config says `[1, 28, 28]`. Leaving
  the batch dimension in is the classic mistake; `test_client.py::case_config_matches_engine`
  cross-checks the config against the engine's own shapes for exactly this reason.
+ **A per-sample scalar cannot be written as an empty `dims`.** The output `z` has engine shape
  `(-1,)`, i.e. nothing left after the batch dimension, so it is declared `dims: [1]` with
  `reshape { shape: [] }`.
+ **`max_batch_size` has to stay inside the engine's optimization profile.** The engine here is
  built with `min 1 / opt 4 / max 16`, so the config may not ask for more than 16.

## Getting `tritonserver` without docker (verified here)

A container image is just tar files behind an HTTP API, and NGC serves this repository to
anonymous tokens, so the server can be unpacked directly — no docker daemon, no root, no
`apt install`, and no source build:

```bash
./install-tritonserver-without-docker.sh -o /work/tritonserver-install
export TRITONSERVER_BIN=/work/tritonserver-install/opt/tritonserver/bin/tritonserver
export LD_LIBRARY_PATH=/work/tritonserver-install/opt/tritonserver/lib:$LD_LIBRARY_PATH
python3 main.py
```

What the script does and what was measured doing it:

| Step | Detail |
| ---- | ------ |
| anonymous token | `https://nvcr.io/proxy_auth?scope=repository:nvidia/tritonserver:pull` — **the token expires in about a minute**, so it is refreshed per blob; a stale token returns a JSON error body where a `.tar.gz` is expected, which `tar` reports as "not in gzip format" |
| pick the image | `26.07-py3` reports `TRT_VERSION=11.1.0.106`, **exactly the TensorRT of this container** — that is why the engine built by `main.py` loads |
| extract | only `opt/tritonserver/{bin,lib,backends/tensorrt}` out of the one 1.9 GB layer that holds them → **53 MB** installed |
| two missing libraries | the binary needs `libb64.so.0d` and `libdcgm.so.4`, which live outside `/opt/tritonserver`; they are pulled from the Ubuntu and CUDA `.deb` archives and unpacked with `dpkg-deb -x` (no root) |
| `--backend-directory` | the default is the hard-coded `/opt/tritonserver/backends`; an install elsewhere fails with `unable to find backend library for backend 'tensorrt'`, which does not mention the directory. `main.py` derives the flag from the binary path |

End-to-end result on this machine (**B200**, TensorRT 11.1.0.106, Triton 2.71.0 / 26.07,
re-measured 2026-09-06):

```txt
    Server ready after 2.0 s
    Model metadata: {"name": "mnist-cnn", "platform": "tensorrt_plan", "inputs": [...]}
    Inference over HTTP: 7.23 ms
    Compared with the local reference: max |diff| = 0.000e+00, same argmax = True
    Server stopped with code 0
```

Two caveats: the host glibc has to be new enough for the image (Ubuntu 24.04 here, same as the
image), and this is *not* a supported installation — nothing outside `bin/`, `lib/` and the one
backend is present, so the Python / PyTorch / ONNX-Runtime backends are missing. For anything
beyond one TensorRT model, use the container.

## Running it for real

The engine and the server must come from the **same TensorRT version** — a plan built here
(TensorRT 11.1.0.106) will be rejected by a Triton container whose `tensorrt` backend links
against a different one, with `Engine plan file is generated on an incompatible version`.
The simplest way to keep them in step is to build inside the Triton container:

```bash
docker run --gpus all -it --rm --network host \
    -v $(pwd):/workspace/cookbook -w /workspace/cookbook/07-Tool/TritonServerDeploy \
    nvcr.io/nvidia/tritonserver:<yy.mm>-py3 \
    bash -c "pip install requests && python3 main.py --onnx=../../00-Data/model/model-trained.onnx"
```

Serving an already-built repository by hand is the usual two-terminal version:

```bash
tritonserver --model-repository=$(pwd)/model_repository        # terminal 1
curl -s localhost:8000/v2/health/ready -o /dev/null -w '%{http_code}\n'   # terminal 2
```

## The client

`main.py` speaks the **KServe v2 HTTP protocol** with plain `requests`, because that is one
dependency instead of two and the protocol is just JSON:

```python
payload = {
    "inputs": [{"name": "x", "shape": [4, 1, 28, 28], "datatype": "FP32", "data": [...]}],
    "outputs": [{"name": "y"}, {"name": "z"}],
}
requests.post(f"http://127.0.0.1:8000/v2/models/mnist-cnn/infer", json=payload)
```

The official client library does the same thing with typed helpers and a binary (non-JSON) tensor
encoding, which matters as soon as the tensors are large:

```bash
pip install tritonclient[http]
```

```python
import numpy as np
import tritonclient.http as httpclient

client = httpclient.InferenceServerClient(url="127.0.0.1:8000")
tensor = httpclient.InferInput("x", [4, 1, 28, 28], "FP32")
tensor.set_data_from_numpy(input_data)
result = client.infer("mnist-cnn", [tensor], outputs=[httpclient.InferRequestedOutput("y")])
print(result.as_numpy("y"))
```

## Endpoints worth knowing

| Endpoint | Use |
| -------- | --- |
| `GET /v2/health/ready` | 200 once every model is loaded — what `main.py` polls |
| `GET /v2/health/live` | the process is up, which is **not** the same as ready |
| `GET /v2/models/<name>` | metadata: the tensor names, dtypes and shapes Triton believes in |
| `GET /v2/models/<name>/stats` | per-model request / queue / compute time counters |
| `POST /v2/models/<name>/infer` | inference |
| `GET /metrics` (port 8002) | Prometheus metrics |
