# TensorRT 11.3 的变化与新增范例候选

本轮环境：**TensorRT 11.3.0.99**，B200 ×2，2026-10-14。对比基准是 `07-Tool/ListAPIs/output/` 里已存的
快照。

## 先说一个口径问题：没有 11.2 的快照

`07-Tool/ListAPIs/output/` 里有 `11.0.0.114`、`11.1.0.2`、`11.1.0.106`，**没有 11.2**。所以下面的对比
实际上是 **11.0 → 11.3** 和 **11.1 → 11.3**，11.2 这一格是空的。

间接旁证：早先对 TensorRT-OSS 的调研里记录过公开 `main` 分支在 11.2.1.2 时的 trtexec 选项集，本文末尾
用到了那份数据，但那是**源码层面**的，和 `--help` 的口径不同，不能直接相减。

补救办法只有一个：以后每次换版本，**先跑一次 `07-Tool/ListAPIs`** 再做别的。本轮的 11.3 快照已经补进
`output/`。

## 一、Python API 的变化：比想象中小得多

用结构化比对（按 `类.成员` 提取集合再做差集），而不是 `diff` 行对行 —— 后者报 15384 行变化，**全部是
噪声**：新版 pybind11-stubgen 不再在 `__members__` 后面写 ` # value` 注释，80 个枚举因此全部"变化"。

| 对比 | 新增 | 删除 | 真实修改 |
| :-- | --: | --: | --: |
| 11.1.0.106 → 11.3.0.99 | **1 个枚举 + 1 个属性** | 0 | 0 |
| 11.0.0.114 → 11.3.0.99 | 上面那些，**加 2 个 `IBuilderConfig` 属性** | 0 | 0 |

展开说就是三件事：

### 1. `DLAWorkspaceAllocationStrategy`（11.2 或 11.3 新增）

落地区间已缩到最小：`11.0.0.114` 没有，`11.1.0.2` 没有，`11.1.0.106` 也没有 —— 所以它是 **11.2 或
11.3** 引入的，没有 11.2 快照就再也分不出来了。

```python
trt.DLAWorkspaceAllocationStrategy.DEFAULT        # 每个 DLA module 各自分配 workspace
trt.DLAWorkspaceAllocationStrategy.SHARED_STATIC  # 同一 runtime、同一 DLA core 的 module 共享静态池
runtime.dla_workspace_allocation_strategy          # 默认 DEFAULT
```

文档原文里有一条醒目的警告：

> **warning**: Concurrent execution of engines that share DLA workspace results in undefined behavior.

trtexec 侧对应 `--dlaWorkspaceAllocationStrategy`，**本版已公开**（早先调研内部 11.5 时它还在"内部独有"
那张表里）。

### 2. `IBuilderConfig.build_route` / `all_build_routes`（11.1 新增，我们一直没用）

这两个在 `11.1.0.2` 里**还没有**、在 `11.1.0.106` 里**已经有**，所以是 11.1 这一轮小版本中途加进去的，
严格说不是 11.3 的新东西 —— 但 **cookbook 至今没有任何例子碰
过它们**，而 `07-Tool/trtexec/README.md` 已经把 CLI 那一侧（`--tuneBuildRoutes` / `--setBuildRoute` /
`--helpBuildRoute`）写得很详细。这是一个纯粹的空白。

实测可用，而且效果可测：

```python
config.all_build_routes   # -> JSON 字符串，44361 字符
#   {"tuner_version": "2.21.55", "tuner_options": [ {option, allowed_values, default_value, help}, ... ]}
config.build_route = "-conv_use_long_w=off"   # 赋值成功，读回一致
```

| | 11.1（README 记录） | 11.3（本轮实测） |
| :-- | :-- | :-- |
| `tuner_version` | 2.19.45 | **2.21.55** |
| 旋钮数 | 209 | **215** |

同一个 MNIST 网络换三条 route，产出三种不同大小的 engine（13,269,148 / 13,270,532 / 13,273,004 B），
说明 `build_route` 确实作用到了构建上，不是摆设。

### 3. 没有任何 API 被删除

11.0 → 11.3 删除数为 0。对一个跨两个小版本的升级来说，这本身是个值得记下的结论 —— 和 10.x → 11.0 那次
成批移除（弱类型、`EXPLICIT_BATCH`、INT8 校准器）完全不是一回事。

## 二、Python API 之外的变化

### 内置 plugin：44 → 45

| | 11.0.0.114（`05-Plugin/DefaultPlugin/README.md` 记录） | 11.3.0.99（实测） |
| :-- | --: | --: |
| 不同 plugin 名 | 44 | **45** |
| creator 数 | 69 | **70** |
| `IPluginCreatorV3One` | 19 | **20** |

新增的那一个是 **`FFTPlugin`**，并且是 `IPluginCreatorV3One`。这和早先对内部仓库的调研对得上：当时
`fftPlugin` 在内部树（11.5）里存在、在公开的 11.0 里没有，现在它随 11.2/11.3 公开发布了。

### trtexec：两个曾经"内部独有"的选项已公开

+ `--dlaWorkspaceAllocationStrategy`（配合上面的新枚举）
+ `--dumpCheckerBlob` / `--loadCheckerBlob` —— 帮助文本说明它**只在 `--safe` 下可用**：构建时写出
  kernel 源码与元数据的 checker blob，校验时再读回来。早先调研公开 `main`(11.2.1.2) 时这两个还在
  "内部独有"那一档。

仍然没有公开的：`--fp16` / `--bf16` / `--int4` / `--fp8` / `--precisionConstraints` /
`--layerPrecisions`（强类型之后这批不会回来了）、`--useGpu` / `--computeCapabilities`（TensorRT-RTX
专属）、`--greenContext`。

### 明确不做

+ **为"80 个枚举变化"写任何东西** —— 那是 stubgen 的注释差异，不是 API 变化。记在这里是为了防止下次
  有人重新"发现"它。
+ **任何 DLA 相关的例子** —— 见 N4。
+ **把 `build_route` 包装成一个调参工具** —— `07-Tool/QDQPlacementAutotune` 已经证明过，在 MNIST 规模
  上这类搜索的收益（1.174x）小于运行间噪声。N1 的定位是**展示 API 和那份旋钮数据库**，不是再做一个
  调参器。

### 回归 1：`02-API/Layer/QDQStructure` —— 真正的 11.x 行为变化

```txt
RuntimeError: Could not get block_shape.
  在 check_api_coverage(layer_q) -> analyze_public_members -> getattr(target, x)
```

隔离到最小复现：

```python
q = network.add_quantize(tensor, scalar_scale, trt.DataType.INT8)   # 逐张量量化
q.axis         # -> -1          正常
q.to_type      # -> DataType.INT8  正常
q.block_shape  # -> RuntimeError: Could not get block_shape.
```

**在不是块量化的 `IQuantizeLayer` 上读 `block_shape` 会抛异常。** 11.0 的全盘测试（2026-09-08，
257/257）通过，所以这是 11.1 / 11.2 / 11.3 之间引入的行为变化。

**这条最有方法论价值的地方在于：API 快照比对看不见它。** `block_shape` 在 11.0.0.114、11.1.0.106、
11.3.0.99 三份 stub 里**完全一样**（各出现 9 次），变的是 getter 的运行时行为。**stub diff 只能看见
签名，看不见语义** —— 所以"跑一遍全盘测试"和"比一遍 API"是两件不能互相替代的事，这一轮正好各抓到
一条对方抓不到的东西。

影响面已实测，比一开始担心的小：全树有 **67** 个例子调用 `check_api_coverage`，其中 5 个同时出现
quantize/dequantize 层，但另外 4 个（`AttentionStructure` / `Constant` / `Convolution` /
`Deconvolution`）把它用在别的层类型上，本轮日志里都没有 traceback。**目前只有 `QDQStructure` 一个中招**
—— 不过任何以后对 Q/DQ 层调用 `check_api_coverage` 的新例子都会踩上。

修法在共享工具里 —— `tensorrt_cookbook/utils_cookbook.py` 的 `_collect()` 直接用了裸 `getattr`：

```python
ca = sorted(x for x in pub - ... if callable(getattr(target, x)))   # 属性一抛就整个挂掉
```

而 `07-Tool/ListAPIs` 的独立版里**早就有**现成的解法，照搬即可：

```python
def safe_getattr(obj, name):
    try:    return True, getattr(obj, name), None
    except Exception as error:  return False, None, f"{type(error).__name__}: {error}"
```

**尚未改动** —— 这要动 `tensorrt_cookbook/`，等你点头。

### 回归 2：`02-API/BuilderFlag` —— 我们自己的断言不安全（而且是间歇性的）

```txt
AssertionError
  assert size_dict["VERSION_COMPATIBLE + EXCLUDE_LEAN_RUNTIME"] == size_dict["baseline"]
    baseline                                                 56,044 B
    VERSION_COMPATIBLE + EXCLUDE_LEAN_RUNTIME                56,276 B
```

**这不是 11.3 的 bug，是我们这条断言本来就不安全，而且它是*间歇性*的** —— 同一个 main.py 连跑两遍，
第一遍 `baseline 56,180 / VC+EXCLUDE 56,044`（失败），第二遍两者都是 `56,044`（通过）。也就是说这条用例
在 11.3 上会随机红绿。 engine 字节数在两次独立构建之间就不是稳定的 ——
用一个只有一个 MatMul 的网络连测三轮：

```txt
run 0: baseline 27,252 B | VC+EXCLUDE 27,252 B | delta  +0 B
run 1: baseline 27,252 B | VC+EXCLUDE 27,252 B | delta  +0 B
run 2: baseline 27,196 B | VC+EXCLUDE 27,252 B | delta +56 B
```

第 2 轮连 **baseline 自己**都和前两轮差了 56 字节。在 MNIST 规模上更明显（同一组 flag 两次构建差
6,304 B）。所以这条断言在 11.0 / 11.1 上通过是运气，不是保证。

这正是 `README.md` §2.1 最后那条教训的复发：**断言不变量，不要断言观察到的现象**。建议改成断言真正
重要的性质：

```python
# VC + EXCLUDE_LEAN_RUNTIME 应当回到 baseline 量级，而不是逐字节相等
assert size_dict["VERSION_COMPATIBLE + EXCLUDE_LEAN_RUNTIME"] < size_dict["VERSION_COMPATIBLE"] / 100
assert abs(size_dict["VERSION_COMPATIBLE + EXCLUDE_LEAN_RUNTIME"] - size_dict["baseline"]) < 4096
```

**尚未改动** —— 改断言让测试通过是需要先说清楚再做的事，等你点头。
